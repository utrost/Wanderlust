# Android test APK updates

Test APK releases now use one persistent, private test signing key and build
number `1000 + github.run_number` from the **Test APK** workflow. New workflow
runs increase the version; retrying the same run keeps its version. Keep that
workflow's run counter when changing the build pipeline. Android rejects a
downgrade to an older build.

The workflow requires the `WANDERLUST_TEST_KEYSTORE` Actions secret (base64 JKS,
the conventional Android debug alias/password). The private key must never be
committed. A protected local backup lives in the ignored `.local/signing/`
directory. Back it up securely before deleting this checkout. GitHub does not
allow reading a secret back after upload. These are still debug APKs, not a
production signing/distribution setup.

The public certificate SHA-256 is pinned in
`tools/android/test-signing.sha256`. `tools/install_test_signing.py` refuses
missing credentials and certificates that differ from the pin. There is no
fallback to a random key. The credential is installed in the runner's temporary
directory, separate from Gradle's default debug keystores. After compilation,
`tools/sign_test_apk.py` explicitly signs the finished APK and uses
`tools/verify_android_release.py` to verify its signature, pinned certificate,
application ID and version code before replacing the build output. The runner's
key is removed in an always-run cleanup step.

## One-time transition

Earlier test releases used disposable runner keys. Their private keys cannot
be recovered from the APK. Moving from those builds requires one final backup,
uninstall, install and restore. Current full backups include walks, memories,
photos, offline maps and settings. Older backup versions may require downloading
maps and choosing settings again.

Afterwards, download a newer APK and install it over Wanderlust. Do not uninstall:
Android retains the database, saved walks, maps, selection and preferences.
Stop and save any active walk before installing an update.

## Provisioning status

The persistent test key is provisioned in the repository Actions secret. Its
public certificate matches the committed pin. A private local backup remains
in the ignored signing directory; neither the key nor its base64 encoding is
part of the repository.

On Android API 35, builds 990 and 991 signed with the prepared key passed APK

## Store candidates (0.1.0)

`Store candidate` is a separate, manually dispatched workflow. It builds an
optimised, **unsigned** APK and AAB and uploads Actions artifacts. It does not
publish a GitHub release or submit to either store. Build numbers use a separate
100000 + workflow-run sequence, above the test series. Do not install a high-code
candidate on your daily device if you intend to return to lower-code test builds.

The tracked Android Gradle overlay targets API 36 and uses NDK 28.2.13676358.
`tools/toolchain.env`, `Cargo.lock`, and `app/pubspec.lock` pin the toolchains and
libraries. The Android scaffold is still generated by the pinned Flutter SDK;
`configure_android.py` replaces its app Gradle file, backup rules and launcher
icon. `prepare_android.sh` refuses an unexpected Flutter version. Update pins
and lockfiles deliberately, together with tests and licence notices.

Build from a clean checkout using the pinned tools:

```sh
bash tools/prepare_android.sh
cd app
flutter pub get --enforce-lockfile
flutter build apk --release --target-platform android-arm64,android-x64 --build-number 100001
flutter build appbundle --release --target-platform android-arm64,android-x64 --build-number 100001
cd ..
python3 tools/verify_store_build.py app/build/app/outputs/flutter-apk/app-release.apk --build-tools "$ANDROID_HOME/build-tools/36.0.0"
python3 tools/verify_store_build.py app/build/app/outputs/bundle/release/app-release.aab
```

The build rejects Google Play Services/Firebase Maven dependencies. Artifact
checks reject debug APKs, incorrect ABIs, missing native exports, missing AOT
libraries, Google SDK references in DEX and ELF load segments below 16 KB
alignment. APK ZIP alignment is checked too. These are packaging checks;
runtime testing on a 16 KB device and Play's bundle validation remain required.

For signing, supply all four environment variables to the build:
`WANDERLUST_RELEASE_KEYSTORE` (absolute path),
`WANDERLUST_RELEASE_STORE_PASSWORD`, `WANDERLUST_RELEASE_KEY_ALIAS`, and
`WANDERLUST_RELEASE_KEY_PASSWORD`. A partial configuration fails rather than
falling back to debug signing. Keep credentials outside the repository and
console logs. No production key is generated or selected automatically.

Before first publication, decide whether Play App Signing, F-Droid signing or
verified upstream signatures own each distribution channel. Preserve the current
application ID unless deliberately accepting a separate installation. Different
certificates cannot normally update each other; the existing **test certificate
is not silently promoted to production**. Keep the manual backup/restore path
available for testers changing signing channels.

## Submission material and outstanding gates

The GitHub repository is currently **private** (checked 2026-09-30). Public
F-Droid source access, usable public support/source links and a public privacy
policy require a publication decision. Do not assume a GitHub source-file URL
works for people outside the repository. Changing repository visibility exposes
its history as well as the current code; review that separately before publishing.


- `fastlane/metadata/android/en-US/`: store copy and artwork. Capture screenshots
  from the final candidate with synthetic or explicitly approved personal data.
- `app/assets/legal/privacy.txt`: policy available offline in About. Matching
  `docs/privacy.html` is ready for public hosting. Set a working, public policy
  URL in Play Console before submission; source files alone are not a deployment.
- Android automatic cloud backups and device transfers explicitly exclude all
  app-private data. Manual full backups remain available. Older backups made by
  previous versions are outside the app's control.
- `fdroid/com.wanderlust.wanderlust.yml`: disabled submission metadata draft.
  Still needs a tagged build recipe validated in fdroidserver, a complete
  dependency/licence scan and signing/reproducibility decisions. Removal of GMS
  alone is not a claim of F-Droid acceptance or bit-for-bit reproducibility.
- Play Console: verified developer account, support contact, audience/content
  rating, privacy/Data Safety review and location foreground-service declaration
  with a demonstration of start, screen-off notification and stop. Overpass
  receives the requested map area and IP; do not blindly declare no data leaves
  the device. No background-location permission is requested.
- Personal accounts subject to Google's new-account rules require a closed test
  before production access. Recruit real testers; emulator tests do not qualify.
- Field gate: one-hour screen-off walk and idle comparison on real phones;
  permission denial/revocation; disabled GPS; kill/reopen recovery; update without
  data loss; backup/restore; low storage and a large offline map.

References: [Play user data](https://support.google.com/googleplay/android-developer/answer/10144311),
[foreground service declaration](https://support.google.com/googleplay/android-developer/answer/13392821),
[F-Droid metadata](https://f-droid.org/docs/Build_Metadata_Reference/).


### Local candidate evaluation — 2026-09-30

146 Flutter tests passed with Rust FFI enabled; two optional live-network tests
were skipped. Flutter analysis was clean, and all 20 Python tooling tests passed.
The pinned scaffold/native preparation completed with the app lockfile preserved.
Release APK and AAB built successfully; both passed native ABI/16 KB ELF checks
and the Google SDK scan. The APK passed 16 KB ZIP alignment and non-debuggable
manifest checks. Deliberately incomplete signing configuration was rejected.

An emulator-only copy of the release APK, signed with that emulator's existing
key, updated without uninstalling: the existing walk, memories and 19 explored
sections survived. With Google Play Services disabled on API 35, GPS recording
worked; distance progressed from about 0.02 to 0.07 km through an 18-second
screen-off interval. Foreground service and partial wake lock were observed.
Stop/relaunch left no recording foreground service or recording wake lock, and
three walks plus memory pins persisted. These are short functional probes, not
battery measurements or a clean AOSP/Android 16/16 KB runtime qualification.

Testing also exposed a pre-existing stationary-memory bug: Geolocator's shared
stream retained the walk's five-metre distance filter. Memory lookup now makes
bounded independent native requests and retries poor fixes. The same stationary
location pinned successfully after the displayed fix had aged, while recording
continued. A regression test verifies it never reuses the recording stream.

Store screenshots use synthetic emulator positions/notes, not the user's traces.
Artwork and copy are drafts for review before store submission.
